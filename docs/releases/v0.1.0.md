# dac-plane v0.1.0

The first supported distribution of dac-plane: a provider-neutral control plane for delegated agent work. It is
intended for independent self-hosted pilots. This release makes no availability, throughput, cost or production
claim, and no support objective has been established.

License: Apache-2.0. Third-party notices are in `/licenses` in each image.

## Highlights

- A durable lifecycle for delegated agent work: tasks, attempts, attention, decisions, budgets, artifacts, audit,
  result revisions and reviews, served through Surface API v1.
- Codex running its commands in E2B sandboxes, with artifacts stored through an S3 adapter.
- An adapter kit and conformance suite, so a provider can be integrated from outside this repository.
- Signed tags, reproducible images with provenance and SBOMs, and a release gate that rebuilds from the tag.

The Codex adapter runs commands in the task's sandbox only (ADR-0016). Running them in the adapter container is not
part of this release, and the published image has no shell.

## Verify what you pull

```sh
gh attestation verify oci://ghcr.io/dac-plane/dac-plane@sha256:DIGEST --repo dac-plane/dac-plane
docker run --rm ghcr.io/dac-plane/dac-plane@sha256:DIGEST version
```

Each image's SBOM, provenance bundle and vulnerability scan are attached to this release, one per architecture. Scanning stops the
release on a fixable HIGH or CRITICAL finding, so unfixed and lower findings may appear in the attached reports.

## Install

Follow [the reference deployment guide](https://github.com/dac-plane/dac-plane/blob/v0.1.0/deploy/compose/README.md).
Set `DAC_PLANE_IMAGE` to the digest from the manifest.

## Upgrading

This is the first release, so there is no supported upgrade into it. A database created by an earlier development
build is not supported. Later releases follow ADR-0011:

1. Check that the new image serves the current schema.
2. Roll every `serve` replica to it while the schema stays unchanged.
3. Confirm that no old process or adapter connection remains.
4. Run the new image's `migrate up`.
5. Check readiness and lifecycle progress.

## Rollback limits

Before a migration, restore the old image against the unchanged schema. After one, an old binary may return only if
the database is inside its serving range; check with `dac-plane migrate status`. `migrate down-to` refuses when a
downgrade would discard durable evidence. Treat that as a stop, and do not delete data to get past it.

## Known limits

- **The published images have not run against live providers.** They pass the build, scan and clean-room checks on
  both architectures. Live evidence comes from local arm64 builds of an earlier commit, so amd64 has none. Qualify
  the digests you deploy before relying on them.
- **A provision can stall.** If E2B takes more than 45 seconds to answer a create, or the reply is lost, and the
  adapter cannot find the sandbox, the attempt stays in `provisioning` until someone cancels the task. It was seen
  once in about 18 live provisions. Cancelling works but can be slow: until the adapter can rule out a late create, it
  waits for the sandbox lifetime plus 5 minutes (`DAC_E2B_SANDBOX_TIMEOUT`, 15 minutes in the reference overlay, so up
  to 20 minutes).
- **The evidence is bounded.** See the [provider qualification note](https://github.com/dac-plane/dac-plane/blob/v0.1.0/docs/architecture/provider-qualification-75.md)
  and [release evidence](https://github.com/dac-plane/dac-plane/blob/v0.1.0/docs/architecture/release-95.md) for what
  was and was not observed. Every provider other than those above is unqualified.
- **Kit API.** While the kit is v0, a minor version may change its Go API (ADR-0018).
- **Codex notices.** `codex-app-server` ships with OpenAI's license and notice. Its archive has no notices for the
  Rust crates compiled into it, so they are not reproduced.
