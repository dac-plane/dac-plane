# dac-plane v0.3.0

This release lets a tenant define the agents it gives work to and govern what those agents can reach in other applications. An agent is a record with a role and standing instructions that tasks are delegated to; a connection lets an agent's work call another application's tools through dac-plane, so every call is authorized, can wait for a person, and is audited. The highlights of this release are:

- Create agents with a role and standing instructions, and delegate tasks to them through the Surface API
- Have a delegated task's runtime receive the agent's instructions apart from the owner's request
- Register a connection to an external application, consent at its connector, and grant an agent or a task some of its tools
- Have every connector call authorized by a grant, held for approval when the grant says ask, refused when revoked, and recorded in the audit trail
- Reach connector tools from Codex through dac-plane's MCP gateway with a token that is valid only for one attempt

This release is for self-hosted pilots. It makes no availability, throughput, cost or production claim, and no support objective has been established. Read [Known limits](#known-limits) before you rely on it.

## Delegating work

### Agents

An agent is a named role a tenant gives work to: a name, a role, optional standing instructions and the default runtime and environment providers. Create one with `POST /agents` and give its `agent_id` when you submit a task. The task records the agent revision it was delegated to, so revising the agent later never changes work already given to it. An agent is not a principal: the task stays owned and authorized by whoever submitted it ([ADR-0020](../adr/0020-agents-are-product-records.md)). See [Delegate work to agents](https://dac-plane.github.io/dac-plane/use/agents/).

### Connections and grants

A connection is a link to one account at an external application, served by a provider in the new `connector` role. Its owner registers it with `POST /connections`, opens the consent URL the connector returns and completes it with the proof the browser receives. The connector keeps the credential: the surface, the runtime, the model, the database, events and artifacts never see it. The owner then grants an agent, or one task, a set of the connection's tools with `ask` or `always`, a call limit and an expiry. Revoking the grant, or removing the connection, refuses the next call at once ([ADR-0022](../adr/0022-govern-connectors-at-a-control-plane-gateway.md), [ADR-0023](../adr/0023-recover-connector-calls-and-credential-removal.md)). See [Connect external applications](https://dac-plane.github.io/dac-plane/use/connectors/).

## Running agents

### The delegated agent's instructions

A runtime adapter that negotiates `agent.instructions` receives the agent's role and instructions beside the brief in `start_turn`. The Codex adapter places them in the thread's developer instructions and keeps the brief as task input. A delegated task whose runtime has no such adapter connected fails before its turn starts instead of running without them ([ADR-0021](../adr/0021-refuse-delegated-turns-at-dispatch.md)).

### The connector gateway

dac-plane serves an MCP endpoint, the connector gateway, on its adapter listener. A runtime adapter that negotiates `connector.gateway` receives the gateway's URL and a token bound to one attempt; the token authorizes nothing at an external application and stops working when the attempt ends. Each tool call is checked against the grants of the task and its agent and the tenant's policy, and only then sent to the connector. The Codex adapter lists the attempt's tools and offers them to the model as plain functions, relaying each call to the gateway, so connector tools work with model providers that drop Codex's namespaced MCP tools ([ADR-0024](../adr/0024-relay-connector-tools-to-codex-as-dynamic-tools.md)). Turn it on with `DAC_CONNECTOR_GATEWAY_URL` and `DAC_CONNECTOR_GATEWAY_KEY`, set together.

## Building on dac-plane

### Adapter kit v0.3.0

The kit adds the `connector` role with `list_tools`, `begin_authorization`, `complete_authorization`, `revoke_connection` and `call_tool`, and two capabilities a runtime adapter may offer: `agent.instructions` and `connector.gateway`. A connector's requests about a connection name no attempt. An adapter built with v0.2.0 keeps working: it is never sent a field it did not negotiate.

```sh
go get github.com/dac-plane/dac-plane/adapterkit@v0.3.0
```

### A GitHub connector

`adapters/github` is a connector adapter for a GitHub App, with PKCE consent, sealed credential storage and three tools. It is built and tested in this repository but is not published as an image in this release; see [Known limits](#known-limits).

## Running dac-plane

### A connector in the development stack

`compose.connector.yaml` adds the simulated connector and turns the gateway on. `just qualify-codex-connector` has a live Codex model call a connector tool through the gateway, once under an `always` grant and once under an `ask` grant that waits for approval.

## Upgrading

Follow ADR-0011, in this order:

1. Roll every `serve` replica and every adapter to the v0.3.0 digests while the schema stays at 16. v0.3.0 serves schema 13 to 18. Agent and connection operations answer `503 not-migrated` until the migration runs; everything else works as before.
2. Confirm that no v0.2.0 process or adapter connection remains.
3. Run the v0.3.0 image's `migrate up`, which takes the database to 18.

Before step 3, roll back by restoring the v0.2.0 digests. After it, v0.2.0 refuses to serve, because it serves only up to 16. `migrate down-to 16` returns the database to its range unless an agent, a connection or a connector registration exists. In that case it refuses, because the downgrade would discard them. Treat the refusal as a stop.

This path runs in CI on every pull request: a v0.2.0 deployment, pulled by digest, is rolled and migrated with a task in flight, and an agent is created and delegated to afterwards.

### Breaking changes

None. The Surface API stays v1; its document moves to 1.2.0 with additions only.

### Notable changes

- Schema 17 adds agents and a task's agent reference. Schema 18 adds connections, connection grants, connector calls and the `connector` registration role.
- `provision register-provider` and `bind-adapter` accept the `connector` role.

## Known limits

The limits in [the v0.2.0 notes](v0.2.0.md#known-limits) still apply.

- **The GitHub connector is not qualified against GitHub.** Its behavior is tested against a fake GitHub service, and the live runner exists, but it has not run against a real GitHub App, so its image is not published.
- **The runtime host's egress is not confined by the reference stack.** Restrict it in your deployment to the model provider and dac-plane, so a runtime cannot call an external application directly. The connectors guide says how to check it.
- **Connection requests reach one replica.** Consent, completion, removal and listing tools are answered by the replica the connector adapter is connected to. Another replica answers `503 connector-unavailable`; retry.
- **Tenant enforcement hooks do not run on connector calls.** The gateway enforces grants and policy itself.
